Dori workflows are versioned, validated definitions containing an ordered list of steps. The executor is not a general DAG scheduler: top-level steps run sequentially, while specific control-flow steps provide branching and bounded parallel iteration.

## Execution Model

### 1. Validated Definitions
Workflow definitions and registered action inputs are validated with shared schemas. A workflow can call deterministic actions or an AI provider; using a workflow does not itself imply an LLM call.

### 2. Branches and Bounded Parallel Iteration
A `branch` selects one nested sequence from a scalar value. A `foreach` processes an array sequentially by default and can opt into bounded concurrency. The executor waits for each parallel batch before moving to the next top-level step.

### 3. Pauses and Human Attention
`review_gate`, `request_input`, and `wait` stop the current execution at a persisted resume point. The engine can later continue from that point after approval, an answer, or the scheduled time.

### 4. Optional Guardrails
Workflows may name input and output guardrails. `ConfidenceGuard` can pause a new run when its trigger contains a numeric confidence below 0.6. `ApprovalGuard`, `PermissionGuard`, and `EvidenceGuard` cover narrower output cases.

Output guardrails run after the action has completed. They can stop subsequent steps or request review, but they cannot roll back an external call or vault write that already happened. `EvidenceGuard` also passes with a recorded reason when its configured judge is unavailable.

### 5. State and Events
Execution records track step results, status, revision, and resume position. The engine emits events that allow the portal to refresh workflow and attention surfaces without treating the browser as the owner of execution state.
