The supported Dori Desktop path runs a Tauri shell, a local Next.js portal, and a local Node.js engine. Your durable content lives in a provider-backed Markdown and asset tree; SQLite databases and search indexes are operational read models, not replacements for that content.

## Current Architecture at a Glance

| Layer | Current implementation | Important boundary |
| --- | --- | --- |
| **Desktop host** | Tauri v2 supervises the portal and engine and renders through the operating system webview. | Dori does not bundle Electron's Chromium runtime, although some engine dependencies still include platform-specific binaries. |
| **User content** | Markdown and assets are accessed through a configured vault provider. GitHub is the supported default remote; local filesystem, Google Drive, and OneDrive providers also exist. | Provider capabilities differ, and remote providers necessarily exchange data with their services. |
| **Operational state** | The engine uses SQLite for jobs and domain state; the portal has a separate SQLite store for portal-owned metadata. | These databases are not the canonical store for user-authored content. |
| **Search** | A separate `vectors.db` combines SQLite FTS5 keyword search with locally computed embeddings and cosine similarity. | The index is derived and rebuildable. It is not the vault. |
| **AI calls** | Configured CLI or API providers are selected through an ordered provider chain, with optional `fast`, `standard`, and `reasoning` model tiers. | Cloud API providers receive the prompt and context needed for the request. Dori does not currently configure provider prompt caching. |
| **Workflows** | Ordered workflow steps support conditions, branches, bounded parallel `foreach`, pauses, and optional guardrails. | Output guardrails run after an action and can halt or pause subsequent work; they cannot undo a completed side effect. |
