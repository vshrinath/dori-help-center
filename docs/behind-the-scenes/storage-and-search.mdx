Dori separates durable user content from operational state and derived search data.

## Storage & Search Architecture

### 1. User-Owned Content
Markdown files and assets live behind the configured vault provider. The local filesystem is one provider; GitHub, Google Drive, and OneDrive are remote provider options. These files remain the canonical user-content layer.

### 2. Operational SQLite
On the supported Desktop path, the engine stores jobs, workflows, and domain state in SQLite behind its data-layer stores. The portal maintains a separate SQLite database for portal-owned metadata. These databases are not a single store and do not replace the vault.

### 3. Rebuildable Hybrid Search
The engine keeps a separate `vectors.db` cache. It indexes text in SQLite FTS5, computes embeddings locally with a Transformers model, compares vectors in-process with cosine similarity, and combines keyword and vector result lists with reciprocal-rank fusion. If embedding fails, a chunk remains keyword-searchable.

### 4. Index Updates
Search rows include a truncated SHA-256 content hash for provenance. Current incremental backfill skips files using modification time; ordinary ingestion can recompute embeddings when a file is re-ingested. The search database is therefore a disposable cache that can be cleared and rebuilt, not a content-addressable store that guarantees hash-based short-circuiting.
