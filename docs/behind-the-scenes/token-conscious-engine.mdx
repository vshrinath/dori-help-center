## 1. Provider Selection

Dori keeps an ordered provider list. A call can also pin one provider, in which case Dori fails loudly when that provider is unavailable instead of silently substituting another. Unpinned fallback to a later provider requires the configured workflow-AI consent.

Callers can request a provider-agnostic model tier: `fast`, `standard`, `reasoning`, or `inherit`. The selected provider resolves the tier to a concrete model when its catalog supports that distinction.

---

## 2. Tools and Context

Chat can expose scope-filtered Universal Actions as tools. The model may call actions such as memory search, and Dori executes those calls through the same registered action boundary used elsewhere. A memory-search result can supply targeted vault excerpts and record them as sources for the turn.

The current chat path sends the conversation history supplied by the caller. Retrieval is available through tools, but there is no universal pre-LLM gate that automatically replaces every locally answerable request with a zero-token lookup.

## 3. Validation and Guardrails

Tool inputs are schema-checked at the action boundary. Some single-turn AI calls request JSON and required keys; malformed responses can trigger bounded retries.

Workflow guardrails are opt-in. Input guards run before the first step. Output guards run after a non-read-only action has already taken effect, so they can stop or pause later execution but cannot undo that action. `EvidenceGuard` uses a pinned OpenAI judge for groundedness when configured and passes with a recorded skip reason when the judge is unavailable.

## 4. Current Limits

Dori does not currently configure provider prompt caching, report cache-hit usage, redact arbitrary prompt content at the provider boundary, or automatically retry a failed guardrail until it passes. Those behaviors should not be inferred from the presence of schemas, local search, or guardrail definitions.
